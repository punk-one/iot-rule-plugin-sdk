## 3. 分级发现

### SDK-001（P0）兼容性基线只检查名称，无法支撑三年承诺

证据：

- `tests/api_surface_test.go` 只通过 Go AST 收集根包的导出声明名称并比较集合。
- 未比较函数/方法签名、接口方法集、结构体字段、字段标签、常量值或别名目标。
- `legacy_compat.go` 暴露大量 `net/rpc` DTO，但这些 DTO 的字段没有机器可验证基线。
- 握手值、插件名称和错误前缀分别散落在 `internal/transport/handshake.go`、`internal/transport/serve.go`、`internal/core/errors.go`，没有协议快照测试。

影响：修改 `Plugin.OnEvent` 参数、给 `RuntimeContext` 增加方法、修改 `StartArgs` 字段类型、改变 JSON/Gob 字段名或握手值，都可能让旧插件无法编译或无法被引擎加载，而现有 API 测试仍通过。

建议：建立完整的 v1 契约清单和自动门禁，至少包括：

1. Go API 签名差异检测，而不只是名称集合。
2. 接口方法集、导出结构体字段顺序/类型/标签、常量值快照。
3. 握手 `ProtocolVersion=1`、`PUNK_PLUGIN_MAGIC`、`punk-rule-engine` 和 dispense key `plugin`/`connector` 的金丝雀测试。
4. 所有 RPC 服务名、方法名、参数/返回 DTO 和错误前缀的 golden fixture。
5. `v1.0.0` 旧插件二进制对新引擎，以及新 SDK 基础功能插件对最老受支持引擎的双向测试。

### SDK-002（P1）RPC 超时不能取消底层调用，且多个关键调用没有超时

证据：

- `internal/transport/rpc_call.go` 为每次超时调用启动 goroutine，但 `net/rpc.Client.Call` 本身不会被 context 取消。
- 超时只让调用方返回；底层 goroutine会一直等待到连接恢复或关闭。连续网络异常可能积累 goroutine。
- `EngineRPCClient` 的 Emit、日志、指标、状态、Connector 等多数方法直接调用 `client.Call`，没有统一超时。
- `PluginRPCClient.Info()` 和 `Start()` 也直接调用 `Client.Call`；默认 30 秒仅覆盖部分方法。

影响：引擎或插件进程半开、RPC 服务卡死时，事件协程、停止流程或健康上报可能永久阻塞；超时重试会放大 goroutine 与内存占用。

建议：由连接生命周期实现真正的取消/关闭；所有 RPC 明确 deadline；区分 Info/Start/Stop、事件、状态和长轮询超时；增加半开连接、连续超时和 goroutine 数不增长测试。

### SDK-003（P1）健康上报存在“返回成功但消息未送达”的语义

证据：

- `internal/healthruntime/runtime.go` 的有界队列满时直接丢弃消息并返回 `nil`。
- sender 错误在运行循环中被忽略。
- 状态去重时间在入队前更新，因此被丢弃的状态仍可能在 `MaxSilencePeriod` 内被抑制。
- `Close()` 关闭停止通道后立即返回，不等待队列排空。

影响：插件认为 Unhealthy/Recovering/Stopped 已成功上报，但引擎可能从未收到；在故障风暴和关闭阶段最容易发生，恰好是健康信息最重要的时刻。

建议：至少对状态变化采用“最后状态必达”槽位或带策略的阻塞；记录 dropped/sender-error 指标；只有成功发送后才更新已发送状态；提供带超时的 `Flush/Close` 语义。心跳允许合并，状态变化不应无声丢弃。

### SDK-004（P1）无 Connector 时的默认实现会把失败伪装成成功

证据：`internal/runtime/context.go` 的 `noopConnectorClient` 对 Read/Write/BatchRead/BatchWrite 返回空响应和 `nil`，OpenStream 返回 `(nil, nil)`。

影响：错误绑定或引擎桥接缺失时，插件可能继续运行、产生空数据，或者在使用 nil stream 时崩溃；故障不能被快速定位。

建议：无能力时返回稳定的结构化 `not_implemented`/`unavailable` 错误；只有显式声明“允许空操作”的测试替身才返回成功。

### SDK-005（P1）发布级竞态与覆盖率门禁尚未建立

证据：

- `go test -race ./...` 因健康测试桩未同步而失败。
- 总体覆盖率 16.3%。`internal/transport`、`internal/healthruntime`、`internal/core` 直接覆盖率为 0%，黑盒测试虽会触达部分代码，但覆盖报告没有跨包计入且关键失败路径缺少专门用例。
- 没有 CI 配置，无法证明每次提交都执行测试、竞态、API diff 和构建矩阵。

影响：三年维护期内回归只能依赖开发者手工执行，兼容承诺不可审计。

整改状态（2026-09-05）：健康上报测试桩已增加同步快照访问，`go test -race ./...` 全量通过；CI、完整契约 diff 和示例构建门禁均已建立。首个公开 tag 仍需产出真实旧插件二进制 fixture。

建议：修复测试桩同步；CI 强制普通测试、`-race`、vet、API/协议 diff、示例构建、旧二进制兼容测试；为 RPC 超时、队列溢出、关闭排空、错误编码损坏、并发 Stream、进程崩溃补测试。

### SDK-006（P1）核心接口不适合直接扩展

证据：`Plugin`、`ConnectorPlugin`、`RuntimeContext`、`Logger`、`Emitter`、`ConnectorClient` 和 `StreamConsumer` 都是由使用方实现或模拟的公开接口。

影响：给其中任一接口增加方法都会让已有插件或测试替身无法编译，属于 v2 级破坏。`ConnectorPlugin` 当前尤其宽，流式方法与普通请求方法强耦合。

建议：v1 期间冻结这些方法集。新增能力使用小型可选接口和 capability negotiation，例如由宿主做类型断言；不要向现有接口追加方法。新的请求字段优先放入版本化载荷或新类型。

### SDK-007（P2）StreamConsumer 并发契约不明确

证据：`engineStreamConsumer` 内部 `buffer` 和 `closeOnce bool` 无锁；公开接口文档没有声明单 goroutine 使用还是并发安全。

影响：插件若并发 Recv/Ack/Close，可能发生竞态、重复关闭或缓冲区损坏。

建议：明确 v1 契约。推荐让实现支持并发安全；若暂不支持，必须在接口文档和测试中明确“Recv 与 Close 不可并发”，并由上层生命周期保证。

### SDK-008（P2）事件 ID 不具备强唯一性保证

证据：`NewEvent` 使用 `evt_<UnixNano>` 生成 ID。

影响：高并发或低精度时钟环境存在碰撞可能，会影响去重、Ack 和追踪。

建议：保持现有格式兼容的前提下评估随机/单调组成；先补并发唯一性测试和 ID 契约说明。

### SDK-009（P2）仓库发布治理不完整

证据：缺少 LICENSE 文件、CI、SECURITY、CONTRIBUTING；README 声明 Apache 2.0 但仓库没有许可证正文；README 引用了不存在的两份文档。

影响：外部插件作者无法明确使用条件、漏洞报告流程和兼容规则；文档入口失真。

建议：在首个公开 release 前补齐仓库治理文件和文档链接校验。许可证属于发布阻断项。

### SDK-010（P2）握手配置是可变的导出变量

证据：`plugin.go` 通过 `var HandshakeConfig = transport.HandshakeConfig` 导出结构体变量。

影响：任意使用方都能在运行期修改握手值，产生难定位的不兼容；也扩大了三年冻结面。

建议：v1 不能直接删除该变量。应先文档化为只读契约，并在内部加载路径复制固定值；后续新增返回副本的函数，直到 v2 才考虑收窄。

## 4. 正面能力

- 公共 API 与 `internal` 实现隔离，类型别名减少重复模型。
- 结构化错误能跨 RPC 保留 retryable/skippable/fatal/batch-unsupported 语义。
- Batch 不支持时自动逐条回退，有黑盒测试覆盖。
- 健康运行时具备去重、心跳、队列和序号设计，资源事件轮询具备退避和可观测指标。
- Connector descriptor/binding capability 为引擎和 UI 做兼容性过滤提供了扩展点。
- 旧握手标识被保留，有利于承接旧插件二进制。

## 6. 三年维护判断

如果执行 `docs/v1-compatibility-policy.md` 中的政策并把门禁自动化，当前架构可以维持三年 `v1.x` 演进，无需升级到 v2。扩展的关键原则是：

- 不给使用方实现的接口增加方法；
- 不修改已有 RPC DTO 字段类型/语义；
- 新能力通过小接口、capability 和新 RPC 方法增量提供；
- 永久保留 v1 握手、旧方法和旧错误解码路径直至承诺期结束；
- 每个 release 用真实旧插件二进制验证，而不是只编译当前源码。

## 8. 单进程多规则实例补充复核（2026-09-05）

在公开 `v1.0.0` 前新增 `PluginFactory` 与 `ServeFactory`。它们没有扩大既有 Plugin
接口方法集；旧 `Serve` 和 RPC 方法保持兼容。`PluginRPC.Server` 在每次 Dispense 时
调用 factory，确保多个规则节点位于同一 OS 进程时仍拥有独立插件对象。

`StartArgs` 末尾新增向后兼容的 `BrokerID uint32` 字段。新版引擎为每个实例分配唯一
MuxBroker ID，旧宿主的零值继续回退到历史值 3。完整 v1 契约快照已重新生成并包含
`plugin_factory` dispense key、factory API 和新 DTO 字段。
